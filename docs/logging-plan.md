# Логирование guard и guard-probe

Дополнение пользователя к ревью от 4 ноября 2026. Ниже сохранены требования к журналу. Реализация находится в `internal/runlog`, `cmd/guard` и `cmd/guard-probe`; фактический охват и результаты проверок см. в [verification.md](verification.md). Этот документ описывает целевой контракт; перечисление требования само по себе не означает, что оно проверено.

## Общий контракт

- Стандартная библиотека Go (`log/slog`), без новой зависимости. Файлы JSONL, UTF-8 без BOM, одна запись на событие. Поля: UTC RFC3339Nano, level, component, buildVersion, PID, runId, operationId, event, duration, outcome, структурированная error. Технические имена событий стабильны, краткое сообщение для UI — по-русски.
- INFO по умолчанию, DEBUG через настройку/флаг. Для обоих EXE добавить `--log-dir`, `--log-level`. Каталог по умолчанию — `logs` рядом с EXE, независимо от текущей рабочей папки. Если недоступен — `%LOCALAPPDATA%\KillSwitch\logs` с явным сообщением о фактическом пути. В диагностике UI показывать путь журналов.
- Отдельные файлы на процесс/запуск: `guard-<UTC>-<PID>-<runId>.jsonl`, `guard-probe-<UTC>-<PID>-<runId>.jsonl`. Ротация по 10 MiB, общий бюджет 100 MiB и хранение 7 дней для каждого компонента; значения настраиваемые. Удалять только собственные завершённые журналы, не активные файлы соседних процессов и не чужие файлы. При исчерпании бюджета активными журналами ограничить запись и сообщить об этом, не удаляя их из-под работающего процесса.
- Файловые логи не должны попадать в stdout: `diagnose --json`, `status`, dry-run остаются валидным JSON. Сообщения об отказе логирования направлять в stderr и статус UI. Runner должен разделять stdout/stderr: текущий CombinedOutput может испортить JSON предупреждением.
- Записывать итог и закрывать журнал до `os.Exit`; покрыть ошибки, отмену и timeout. Отсутствие финальной записи при crash означает незавершённый запуск. Ошибка записи не должна менять результат WFP-команды, блокировать аварийное удаление или подвешивать UI. Не делать бесконечных повторных попыток записи.
- Не записывать секреты, окружение целиком, произвольный полный command line, конфиг целиком, сырые сетевые payload. Допускаются выбранные пути EXE, GUID, коды WFP и адрес явно указанной тестовой цели; описать это в документации. Сетевые ответы — только проверенные поля протокола, размер и результат валидации.

## guard

Логировать начало/конец команды и каждой фазы: валидация, диагностика интерфейса, чтение WFP, построение плана, начало транзакции, add/delete, commit/abort, проверка после операции. Длительность каждой фазы нужна для диагностики зависаний.

Данные: GUID и вычисленный LUID, количество приложений/правил, отпечаток согласованного плана, собственные ключи изменяемых объектов. Ошибка: WinAPI-функция, исходный код в hex, символическое имя при наличии, фаза и сообщение. Не терять числовой код за переводом ошибки.

Разделить исходы: `not_applied`, `applied_verified`, `applied_verification_failed`, `commit_unknown`, `cancelled`. Здесь verified — сверка объектов WFP с планом, а не доказанное отсутствие утечки. Удаление: количество объектов до/после, в том числе «уже пусто».

Передавать operationId из UI в guard. Повторное чтение состояния после мутации связывать с той же операцией. События начала и конца должны позволять увидеть, на какой фазе выполнение остановилось.

## guard-probe

Последующее уточнение пользователя: для простого ручного теста реализовать непрерывный мониторинг согласно `docs/manual-host-test.md`. В этом явно выбранном режиме ошибки не завершают процесс; логировать прекращение и возобновление ответов. Указанное ниже сохранение остановки при первой ошибке относится только к прежним разовым режимам CLI.

Связать runId с существующим ID сетевых маркеров. Записывать mode, target, count, interval, timeout, семейство IP, фактические local/remote socket addresses. Для child — parentRunId, PID ребёнка, путь, exit code; ребёнок пишет отдельный файл.

Для каждого seq: resolve/connect/send/receive либо accept/read/reply, длительность, число байтов, ошибка/timeout, результат сверки ACK. Покрыть tcp, udp, hold, sendto, DNS, listener и child. Итог: запрошенные/выполненные/успешные/ошибочные попытки, завершён ли весь сценарий. Сейчас probe останавливается на первой ошибке: явно отражать неполный запуск, не менять эту семантику молча.

Обнаруженное по коду ограничение: сейчас любая успешно прочитанная строка/датаграмма считается успехом без сверки ACK, а один TCP Read может вернуть только часть сообщения. Перед событием «ACK подтверждён» исправить чтение полного сообщения и сверку ID/seq/отправителя. Пока подтверждения нет, логировать только «получены байты». Listener должен ограничивать длину входа и проверять формат; не сохранять произвольный неограниченный ввод.

Ошибка соединения не доказывает блокировку именно нашими правилами, успешный ответ не доказывает VPN-путь. В журнале фиксировать наблюдение; вывод об отсутствии утечки требует данных приёмника/захвата трафика из протокола испытаний.

## Приёмка

- Тесты JSONL, корреляции и финального события на успехе/ошибке/отмене.
- Stdout остаётся валидным JSON при включённых логах и отказе их записи.
- Проверены ротация, бюджет, параллельные процессы, недоступный каталог, ошибка записи и закрытие журнала до exit. Сбой журнала не препятствует аварийному удалению.
- Probe проверен локальным тестовым приёмником: корректный/неверный/частичный ACK, timeout, hold, listener, child и итог неполного запуска. Unit-тесты не обращаются к внешним адресам.
- В README и протоколе испытаний описаны пути, уровни, ротация, сопоставление operationId/runId с UI и обоими EXE. Передать примеры журналов успешной и ошибочной операций без секретов вместе с результатами тестов.
