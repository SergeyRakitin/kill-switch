# Технический проект Windows VPN Kill Switch

Дата: 4 ноября 2026 года. Документ для реализации на Sol. Версия 0.1 — архитектурный кандидат, не подтверждённая реализация.

Ограничение реализации: экспериментами нельзя прерывать VPN и интернет рабочего компьютера с текущей сессией Codex. Все описанные ниже системные эксперименты сначала относятся к отдельно согласованному изолированному Windows-стенду. Если он недоступен, проверки остаются невыполненными. Подробные границы и порядок разрешений — в начале `implementation-plan.md`; они имеют приоритет над общими формулировками об экспериментах в этом документе.

Утилита должна ограничивать выбранные приложения интерфейсом AmneziaVPN с сохранением запрета при отказах. Предлагается Go CLI и постоянная политика Windows Filtering Platform. Перед установкой на реальные приложения необходимо доказать поведение открытых потоков при смене маршрута, активность фильтров после загрузки и покрытие DNS и посредников. Сейчас эти гарантии не проверены на компьютере пользователя.

## 1 Модель угроз

В области защиты: случайный прямой выход при отключении VPN, изменении маршрутов, недоступности сервера, crash утилиты, смене адресного семейства и перезагрузке. Политика привязана к конкретным image paths и интерфейсу, а не к имени продукта.

Вне гарантии MVP: противодействие локальному администратору, вредоносному драйверу, процессу, сознательно передающему данные произвольному непроконтролированному посреднику через IPC, и компрометации VPN-сервера. Обычные DNS и proxy-пути Claude исследуются обязательно и не исключаются из проверки под этим предлогом.

Инвариант: для покрытого EXE внешний сетевой обмен допускается только при доказанной принадлежности пути доверенному VPN-интерфейсу. Неизвестное состояние означает блокировку либо отказ считать систему защищённой. Пропускная способность VPN и исправность сервера не являются условием снятия блокировки.

## 2 Установленные факты и открытые вопросы

Microsoft перечисляет ALE_APP_ID, IP_LOCAL_INTERFACE и IP_NEXTHOP_INTERFACE среди условий ALE_AUTH_CONNECT для соответствующих Windows-версий. Наличие условия в таблице ещё не доказывает его значение для всех повторных авторизаций. На OUTBOUND_IPPACKET в таблице нет ALE_APP_ID: нельзя просто скопировать туда тот же фильтр по приложению [S1, S2].

ALE использует состояние потока: разрешение нового потока не означает отдельную проверку каждого пакета. Документированные причины reauthorization включают изменение политики и arrival interface; этой страницы недостаточно для доказательства всех случаев смены исходящего маршрута [S3].

В tailscale/wf просмотрены firewall.go, compose.go, types.go и syscall.go ветки main. Есть Persistent у provider, sublayer и rule, Dynamic у session, HardAction у rule и внутренние вызовы транзакций. #вывод: библиотека — подходящий кандидат, но её публичный интерфейс транзакций, AppID и нужные типы условий требуется проверить на закреплённой ревизии [S6–S8].

Не проверены: конфигурация компьютера, backend Amnezia, текущие пути Claude, семантика маршрутов на целевой сборке Windows, активация после reboot, все референсные проекты из исходного задания. Технический документ сознательно не выдаёт эти пункты за выполненное исследование.

## 3 Кандидат политики WFP

**Уточнение P2 от 4 ноября 2026 года:** описанная ниже пара A/B не завершает проект политики. Документация Microsoft устанавливает, что при reauthorization outbound flow на входящем ответном пакете `IP_NEXTHOP_INTERFACE` может быть `FWP_EMPTY`; узкое разрешение A не совпадёт, а B может разорвать нормальный поток. Нужен отдельный проверенный сценарий для такого направления, но широкое разрешение по arrival interface до стенда не добавлять. Также CONNECT-only не закрывает inbound-originated flows. Обоснование и ссылки: [исследование](research.md). Все гарантии ниже условные до G3.

Для первого лабораторного прототипа исследовать два слоя: FWPM_LAYER_ALE_AUTH_CONNECT_V4 и FWPM_LAYER_ALE_AUTH_CONNECT_V6. Отдельно исследовать ALE_AUTH_RECV_ACCEPT_V4/V6 для входящих потоков и их ответов. RECV_ACCEPT нельзя механически считать вторым CONNECT: там отличаются направление и доступные значения интерфейсов [S1, S3].

Для каждого разрешённого пути получать бинарный AppID через FwpmGetAppIdFromFileName0 и освобождать результат штатным API. Не собирать blob вручную из пути. Значение интерфейса-кандидата — NET_LUID, сравнение FWP_MATCH_EQUAL по FWPM_CONDITION_IP_NEXTHOP_INTERFACE. Семантику и представление FWP_UINT64 сверить по SDK и runtime metadata до установки [S2, S9].

Предлагаемая схема в одном собственном sublayer на каждом CONNECT-слое:

- Правило A: ALE_APP_ID совпадает; IP_NEXTHOP_INTERFACE равен разрешённому LUID; FLAGS не содержит IS_LOOPBACK. Действие обычный PERMIT, без CLEAR_ACTION_RIGHT. Явный вес FWP_UINT64 = 200.
- Правило B: ALE_APP_ID совпадает. Действие BLOCK. Явный вес FWP_UINT64 = 100.
- Если доверенный интерфейс не определён достоверно, в создаваемом наборе остаётся только B. Не выбирать произвольный активный VPN или адаптер с похожим названием.
- Для IPv6 применять ту же схему только при подтверждённом пути через VPN; иначе полный запрет IPv6 для покрытого EXE.

Это проектные значения весов, не универсальные безопасные константы. Начальный кандидат веса sublayer — 0x8000; он подлежит пересмотру после чтения действующей политики и проверки hard permit. В обоих правилах установить PERSISTENT, выбрать отдельные фиксированные ключи и собственный persistent provider/sublayer. Не применять PERMIT_IF_CALLOUT_UNREGISTERED. Драйверы callout не входят в MVP.

Внутри sublayer правило A должно завершать рассмотрение прежде B. Обычный PERMIT не должен обходить блокировки другого firewall. Между sublayers существуют hard permit и veto; нельзя утверждать, что наш BLOCK безусловно перекрывает любой чужой фильтр. Флаг CLEAR_ACTION_RIGHT и формулировки справочных страниц сверить с SDK и тестом: обзорная статья содержит неоднозначное описание флага [S4, S5].

Почему не основной вариант «APP_ID и interface != VPN → BLOCK»: неизвестное значение поля при reauthorization не обязано вести себя как обычное неравенство. Default deny с узким разрешением делает неуспешное совпадение разрешения блокирующим. Это локальное рассуждение не доказывает, что нужная классификация вообще произойдёт при каждом изменении маршрута.

## 4 Условное обоснование и граница доказательства

При условиях, что поток действительно классифицирован на выбранном слое, AppID совпадает, next-hop достоверен, наш sublayer участвует в принятии решения и нет обходящего hard permit, схема даёт следующие результаты:

1. Доверенный VPN и не-loopback: совпадает A, более низкое B в этом sublayer не применяется; другие политики всё ещё могут запретить соединение.
2. Физический или иной недоверенный интерфейс: A не совпадает, B блокирует.
3. Неизвестный или отсутствующий интерфейс: нет подтверждённого совпадения A, B блокирует; семантику FWP_EMPTY проверить отдельно.
4. Другой AppID: A и B не совпадают, наша политика не меняет решение для этого приложения.

#вывод: это обоснование решения одной классификации, а не доказательство отсутствия утечек в течение жизни потока. Для полной гарантии требуется наблюдение reauthorization и фактических пакетов TCP/UDP при смене пути. Успешная вставка фильтров и зелёный status этого не заменяют.

Если классификация не предотвращает прямой пакет уже разрешённого потока, прототип не соответствует задаче. Не исправлять это таймером, паузой процесса или глобальным правилом по локальному IP, затрагивающим другие приложения. Предложить пользователю проверяемую изоляцию сетевой среды либо пересмотр ограничений; собственный драйвер автоматически не добавлять.

## 5 Постоянство и загрузка

Нединамическая сессия и persistent объекты — разные требования. PERSISTENT сохраняет фильтр через остановку и запуск BFE; BOOTTIME применяется до старта BFE и несовместим с PERSISTENT в одном объекте [S5].

Документация FWPM_FILTER0 отдельно описывает DISABLED в зависимости от serviceName provider и автозапуска связанной службы. Поэтому вариант «CLI завершился, служба не нужна, reboot автоматически безопасен» пока является #гипотеза, а не решением [S5].

Обязательный эксперимент: собственный persistent provider, собственный sublayer, правила только для probe; после согласованного reboot прочитать flags и проверить передачу до ручного запуска guard. Если требуется serviceName, не связывать правила с чужой службой. Рассмотреть минимальную собственную службу в том же EXE только после обоснования и согласования изменения требований.

Раннюю загрузку проверять отдельно: persistent не является обещанием защиты до BFE. Если ранний probe может выйти напрямую, требуется другая доказанная схема или согласованное ограничение запуска защищаемых программ. Ограничение нельзя принимать молча.

## 6 Идентификация VPN и восстановление

В пользовательском JSON сохранять GUID и описательные атрибуты интерфейса; на установке сопоставлять их с текущим LUID. Alias служит для отображения. Нельзя считать ifIndex или LUID устойчивыми во всех сценариях пересоздания.

#гипотеза: если фильтр содержит устаревший LUID, разрешение перестанет совпадать и сохранится запрет. Проверить также возможное повторное использование идентификатора другим адаптером; один запрет при отсутствии интерфейса этого риска не закрывает.

Требования «без постоянно работающей службы» и «автоматически восстановить доступ после нового LUID/GUID» потенциально конфликтуют. Сначала выяснить реальный жизненный цикл Amnezia. Если нужен обработчик системных событий, он лишь обновляет узкое разрешение поверх сохраняемой блокировки. Его отсутствие и ошибки должны приводить к потере доступа, а не к разрешению физического интерфейса. Саму необходимость такого компонента согласовать.

trustedVpnServerIPs не использовать как разрешённые назначения Claude. VPN endpoint, next-hop и внешний адрес после NAT — разные сущности. До появления достоверного источника активного peer список допустим только как диагностическая справка с отметкой «не проверено». Проверка публичного IP не входит в механизм безопасности.

## 7 Покрытие приложений и посредников

Правило AppID покрывает конкретный исполняемый файл. Дочерний EXE, сетевой helper, Node, локальный proxy и системный DNS могут создавать собственные соединения. Для каждого требуется определить фактического владельца трафика. Дерево PID помогает исследованию, но не превращает постоянный фильтр по пути в наследуемую политику.

Для общего Node предложить отдельный поддерживаемый runtime с уникальным путём, если он нужен. Не блокировать node.exe других проектов. Для обновляемых Desktop-путей документировать процедуру обновления политики до использования нового EXE. Нельзя обещать автоматическое покрытие любой будущей версии.

Loopback в строгом режиме запрещён. Разрешение localhost по порту не доказывает личность и безопасность proxy. При необходимости локальной связи определить слушающий процесс, ограничить его внешний трафик и проверить цепочку целиком; недоказанную цепочку не включать в безопасный профиль. Это может нарушить локальные функции Claude, и такую несовместимость нужно показать.

DNS через системный resolver проверить уникальными именами и захватом. Нельзя разрешить весь svchost.exe или заблокировать его глобально ради одного приложения. Если невозможно отделить его DNS без системных изменений, показать конфликт с исходными требованиями. Изолированный runtime/сетевой контекст или подтверждённый DNS внутри приложения — кандидаты альтернатив, а не готовые обещания.

Ответы на входящие соединения также создают исходящий трафик. Строгий MVP должен либо обоснованно запретить приём внешних соединений для выбранных AppID на RECV_ACCEPT, либо доказать ограничения таких потоков. CONNECT-only решение не объявлять полным до закрытия этого вопроса.

## 8 Атомарность и восстановление

Все мутации собственного набора выполнять в одной явной WFP-транзакции на одном engine handle. Microsoft описывает Begin, Commit, Abort и отмену незавершённой транзакции при завершении сессии [S10].

Обновление сохраняет старый полный набор до commit; сбой до commit возвращает старую политику. Ошибка после commit требует чтения фактического состояния. Нельзя выполнять универсальный cleanup, удаляющий успешно установленную блокировку. Первая неудачная установка не защищает приложения задним числом: их запуск разрешать только после подтверждения активации.

Идентификаторы provider/sublayer фиксированы, filter keys воспроизводимы для версии политики. Перед удалением проверять принадлежность всех объектов. Отчёт после операции сравнивает фактические поля и flags, а не только количество фильтров.

Аварийное удаление работает без исправного JSON, по вшитым идентификаторам владельца, из повышенной консоли с явным подтверждением. Оно не отключает Windows Firewall/BFE и не сбрасывает чужую политику. До экспериментов команда должна существовать и пройти проверку на собственных тестовых объектах.

## 9 Решение о технологии

Основной выбор — Go, Windows amd64, CGO_ENABLED=0. Библиотеку tailscale/wf брать только после проверки публичных API на закреплённом SHA и тестов сериализации условий. В просмотренной syscall.go есть внутренние функции транзакций; одного их наличия недостаточно для использования через публичный интерфейс.

Если нужны прямые вызовы, реализовать узкую обёртку fwpuclnt.dll через golang.org/x/sys/windows. Не переносить полный firewall. Переход на C#/.NET рассматривать лишь при конкретно подтверждённой чрезмерной сложности ABI/памяти; он сам по себе не решает ограничения WFP, DNS и маршрутизации.

## 10 Что должно быть доказано до выпуска

Закрыть семь вопросов: исходящий next-hop при reauthorization; открытые потоки после смены маршрута; hard permit других providers; активность после reboot; безопасная смена LUID; DNS/proxy/дочерние процессы; входящие потоки. Для каждого необходимы ссылка на механизм, тест, результат и граница применимости.

Матрица T01–T19 и этапы реализации находятся в `implementation-plan.md`. Непроведённые испытания имеют статус NOT RUN. Если IPv6 отсутствует на стенде, нельзя объявить его поддержку проверенной. Другие приложения проверяются отдельным контрольным EXE при доступной сети.
