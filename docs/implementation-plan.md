# Технический план реализации для Sol

Дата: 4 ноября 2026 года. Этот документ сохраняет первоначальный исследовательский план. Текущие продуктовые решения и ручной функциональный сценарий определены более поздними [ревью](review-2026-11-04.md) и [ручным тестом](manual-host-test.md); результаты — в [verification.md](verification.md). Требование стенда ниже относится к расширенным испытаниям отсутствия утечек и не блокирует разрешённый пользователем простой цикл только для probe.

## Обязательное ограничение сохранения связи

Уточнение пользователя от 4 ноября 2026 года имеет приоритет над прежним порядком испытаний: во время реализации нельзя разрывать текущий VPN и доступ в интернет. Рабочая сессия Codex зависит от VPN. Общее поручение «реализуй план» или «запусти тесты» не разрешает нарушать эту связь.

- На рабочем компьютере запрещены автоматические отключение/перезапуск AmneziaVPN, остановка его процессов и служб, отключение адаптеров, изменение маршрутов, метрик, DNS, proxy, блокировка VPN endpoint, сброс сети, остановка BFE/Firewall и перезагрузка Windows.
- Codex, его сетевые помощники, транспорт VPN и общие системные службы не включаются в экспериментальные правила. Не определять их только по предполагаемому имени EXE: при неясном владении трафиком не выполнять мутацию WFP. Не создавать для Codex широкое разрешающее исключение — тестовая политика должна вообще не затрагивать его.
- Обычная разработка: чтение состояния, написание кода, сборка, unit-тесты с подменённым WFP backend и dry-run. Стандартный запуск тестов не должен изменять WFP или сеть; интеграционные тесты отделить явным opt-in и проверкой тестовой среды.
- Первый запуск реальных фильтров и все испытания отказов проводить только на отдельно согласованном изолированном Windows-стенде. Его сетевые действия не должны менять host VPN, физические адаптеры, маршруты или DNS рабочей машины. VM сама по себе не доказывает изоляцию: проверить отсутствие общего изменяемого VPN и вмешательства в host network. Создание VM, виртуальных коммутаторов и установка компонентов требуют отдельного согласования.
- Если стенда нет, закончить код, безопасные проверки и документацию. Сетевые испытания отметить BLOCKED или NOT RUN; не пытаться завершить их на рабочем компьютере ради прохождения G3.
- После успешного стенда применение к реальным приложениям на рабочем компьютере — отдельное решение пользователя. Даже правила только для probe могут содержать ошибку; не обещать нулевой риск системной мутации. Предварительно показать точные объекты и пути, результаты стенда и локальный способ удаления собственных правил, доступный без Codex и интернета.

Проверки, намеренно обрывающие VPN на рабочем компьютере, исключены из текущего разрешения. Вернуться к ним можно лишь после явного изменения этого ограничения пользователем, в отдельное согласованное окно с сохранённой точкой продолжения и доступным локальным восстановлением. Автоматический rollback не является разрешением на временный обрыв и не должен снимать защиту по таймеру.

## 1 Цель и границы

Создать персональную консольную утилиту Windows 11 x64 на Go, ограничивающую сетевые соединения выбранных EXE проверенным интерфейсом AmneziaVPN. Политика fail-closed означает, что ошибка или потеря VPN сохраняет блокировку, а не открывает прямой доступ. Остальные приложения не должны ограничиваться нашей политикой.

Первоначальные предпочтения: один рабочий EXE, JSON, системные WFP API, без CGO, GUI, собственного драйвера, таймеров проверки публичного IP и управления VPN. Пользователь затем запросил окно Windows и портативный JSON, а позднее разрешил поддержку Claude и Codex наравне с другими EXE. Реализованы отдельные `guard-ui.exe`, `guard.exe` и `guard-probe.exe`; фактическое применение правил к работающей агентской сессии не выполнялось.

Полная готовность определяется сетевыми испытаниями, а не успешной компиляцией. Если выбранные ограничения не позволяют выполнить гарантию, результат исследования — конкретное ограничение и предложение альтернативы; нельзя молча уменьшить объём защиты.

## 5 P1 Диагностика только чтением

Собрать минимум данных, необходимых для решения, не выгружать токены, командные строки с секретами, VPN-профили с ключами и весь реестр.

- Windows: edition/build/архитектура; состояние BFE и Windows Firewall, доступность чтения WFP. Отказ доступа отражать явно; повышение только для конкретной необходимой операции.
- Интерфейсы: GUID, alias, description, ifIndex, LUID через системный API, тип, статус, адресные семейства, compartment. Сопоставить физические адаптеры, Amnezia, Tailscale и рабочие VPN. Имя адаптера не является доказательством его назначения.
- Маршруты: таблицы IPv4/IPv6, метрики, next hop, VPN-маршруты и возможные обходные маршруты. Зафиксировать strong/weak host параметры, не менять их.
- DNS: адреса резолверов по интерфейсам и действующие политики разрешения имён. Proxy: наличие системного/пользовательского прокси и переменных окружения; в отчёт только очищенные адреса и имена переменных, без учётных данных.
- Amnezia: версия, путь, установленный сетевой драйвер и реально используемый протокол, насколько это видно без чтения секретов. Не определять протокол по названию приложения.
- Claude Code: путь команды, launcher/shim, фактический исполняемый файл, отдельный runtime Node при наличии. Claude Desktop: путь, возможная упаковка/обновляемые версии, помощники.
- Процессы: PID, parent PID, image path и владелец наблюдаемых TCP/UDP endpoint. Снимок не доказывает отсутствие краткоживущих процессов. Активное воспроизведение задач с сетевым трафиком отложить до согласованного теста.

Базовые средства: `Get-NetAdapter`, `Get-NetIPInterface`, `Get-NetIPAddress`, `Get-NetRoute`, `Get-DnsClientServerAddress`, `Get-NetTCPConnection`, `Get-NetUDPEndpoint`, выборочные CIM-запросы процессов и служб. LUID получать через IP Helper API; ifIndex не записывать как вечный идентификатор.

Выход: `docs/diagnostics.md`, локальные очищенные снимки в `temp/diagnostics/`. Критерий: известны реальные объекты защиты и интерфейс либо по каждому пробелу записана причина. Не помечать обнаружение дочерних процессов как полное покрытие.

## 7 P3 Реализовать диагностику и чистую модель политики

Предлагаемая структура, создавать только используемые пакеты:

```text
cmd/guard/                 CLI
cmd/guard-probe/           только испытательный клиент
internal/config/          схема и валидация
internal/diagnose/         Windows inventory
internal/policy/           план правил без побочных действий
internal/wfp/              узкая Windows API обёртка
internal/state/            чтение действующей политики и сверка
docs/                     решения и пользовательские инструкции
temp/                     локальные снимки и разовые инструменты
```

JSON: `schemaVersion`, `applications` с явными абсолютными путями, `vpnInterface.guid`, `vpnInterface.expectedDescription` как подсказка, `loopbackPolicy` со значением `deny` по умолчанию, необязательные `trustedVpnServerIPs`. LUID вычислять и проверять; не доверять одному имени. Список серверов имеет только диагностический смысл до обоснования достоверной привязки.

Не делать редактирование `enabled` в JSON скрытой командой снятия фильтров. Фактическое включение определяется WFP; отключение выполняется отдельной явной командой. Все форматы, коды возврата и названия ниже — проектируемый контракт, ещё не существующие команды.

`guard diagnose`: чтение и понятный отчёт; `--json` для воспроизводимых снимков. `guard install --dry-run`: проверка конфигурации, список точных add/delete, приложения, layers, условия, flags, веса и предупреждения. Не менять WFP, службы, DNS или VPN. Невалидные данные — ошибка без частичного плана установки.

Компилятор политики детерминированный. Один EXE — отдельный AppID; запрещены маски, каталоги и неявное расширение на общий `node.exe`. Проверять существование и canonical path, UNC/reparse и неоднозначные пути либо поддержать с доказательством, либо отклонить с объяснением. AppID получать штатным API. Изменившийся путь обновлённого Claude требует нового покрытия до запуска новой версии.

Unit-тесты: неизвестный интерфейс; пустой список; неверная версия JSON; повторяющиеся EXE; IPv6; устойчивые идентификаторы; отсутствие глобальных правил; отсутствие PERMIT_IF_CALLOUT_UNREGISTERED; loopback default deny; отсутствие IP VPN-сервера среди разрешённых назначений приложения. Снимок плана проверять по смысловым инвариантам, не только golden-файлом.

Выход: работающие diagnose и dry-run, тесты чистой политики. Критерий: они не изменяют сетевую конфигурацию; в выводе невозможно спутать план с активной защитой.

## 8 P4 Реализовать WFP и управление жизненным циклом

Сначала проверить выбранную версию tailscale/wf небольшими тестами API. Если публичный API не даёт нужной транзакции на одном handle, выбрать минимальную прямую обёртку или обоснованное расширение зависимости. Не доставать приватный handle через unsafe и не изображать атомарность между разными сессиями.

Обёртка: открыть/закрыть engine, получить AppID, перечислить layers/objects, Begin/Commit/Abort, добавить/удалить свои объекты, освободить память. Проверить размеры структур, union, указатели, время жизни памяти и ошибки на Windows amd64. Не требовать C++ toolchain ради генератора: сгенерированные определения должны быть проверены и доступны в сборке.

Использовать фиксированные GUID provider/sublayer, идентификаторы правил и версию политики. Не выбирать чужой provider или службу Windows ради активации фильтров. Persistent выставлять согласованно для зависимостей. Для каждой мутации — один владелец операции, блокировка конкурентных install/disable/uninstall и явная транзакция.

Обновление: прочитать реальные объекты → проверить владение → построить полный новый набор → в одной транзакции заменить свои старые объекты → commit → повторно прочитать и сравнить. При ошибке до commit — abort, старая политика остаётся. При неясном результате commit не удалять всё: сначала перечитать WFP и вывести состояние unknown при невозможности сверки. JSON на диске и WFP не составляют общей транзакции; после сбоя истина устанавливается чтением WFP.

Первичная установка отличается от обновления: если правил раньше не было, rollback оставляет исходное незащищённое состояние. До установки реальные защищаемые приложения должны быть закрыты, а успешная активация подтверждена до запуска. Не обещать, что неустановленный фильтр уже защищает работающий процесс.

`status`: active / blocked / disabled / degraded / unknown с раздельными полями «политика установлена», «интерфейс распознан», «покрытие приложений», «проверка после reboot». Status не является сервисом проверки здоровья VPN. Ошибка чтения не превращается в active.

`disable`: показать последствия, потребовать подтверждение либо явный `--yes`; атомарно удалить только собственные фильтры. `uninstall`: подтверждение, затем свои фильтры и неиспользуемые свои зависимости. Аварийный вариант `uninstall --emergency --yes` не должен зависеть от целостности конфигурации; использовать вшитые GUID и проверку принадлежности объектов. Не трогать чужие правила, BFE, Windows Firewall или Amnezia.

Критерий до G2: meaningful unit-тесты сбоя каждой стадии, конкурентной мутации, неизвестного commit и сверки состояния проходят; подготовлены команды восстановления. Реальное поведение WFP ещё не считается проверенным.

## 9 P5 Подготовить безопасный сетевой стенд

Сначала зафиксировать место запуска: рабочий компьютер или отдельный стенд, его идентификатор и границы сети. Для реальных WFP-экспериментов нужен изолированный стенд по обязательному ограничению в начале плана. Не запускать подготовленные сценарии автоматически на машине текущей сессии.

Испытательный `guard-probe.exe` пишет только тестовые маркеры: TCP connect и удержание с передачей, UDP connected и unconnected SendTo, IPv4/IPv6, DNS через системный resolver и прямой запрос. Должен уметь запустить дочерний probe с другим путём и обратиться к локальному тестовому прокси. QUIC моделировать недостаточно одним UDP connect: реальный QUIC приложения проверить отдельно, если используется.

Задать внешние приёмники под контролем пользователя, адреса, порты, разрешение на трафик и доступность IPv6. Не создавать серверы, не оплачивать инфраструктуру и не рассылать тесты произвольным адресам. Без подходящего приёмника тест отметить как недоступный.

Сопоставлять маркер, время, протокол, локальный и удалённый endpoint, путь EXE, наблюдаемый интерфейс и запись приёмника. До отрицательного теста подтвердить, что приёмник доступен без защиты и VPN исправен в положительном сценарии. Контрольный незащищённый EXE должен работать через обычный маршрут, когда он доступен.

Средство захвата: сначала установленное; допустимость встроенного pktmon и конвертации проверить по текущей системе. Запуск захвата может менять диагностическое состояние и требует обозначения в плане теста. Не ставить Npcap без разрешения. Сохранять только нужные потоки и минимальную длительность, исключая полезную нагрузку реальных Claude.

На физическом интерфейсе ожидается внешний зашифрованный транспорт VPN. Нарушение — прямой пакет к тестовому назначению либо DNS/прокси-обход; нельзя считать любой пакет к VPN-серверу утечкой. Серверный лог и захват дополняют друг друга; отсутствие ответа не доказывает отсутствия исходящего пакета.

Выход: `docs/test-protocol.md`, конфигурация только для probe, рабочий сценарий восстановления. На G2 предъявить конкретные EXE, объекты WFP, действия с сетью и путь восстановления, после чего запросить разрешение.

## 10 P6 Выполнить матрицу испытаний

Матрица описывает целевые проверки продукта, а не разрешение выполнить их на рабочей машине. T02–T04, T06, T08–T10 и любые другие действия, способные прервать рабочую связь, выполнять только на согласованном изолированном стенде. Реальные WFP-эксперименты остальных строк также сначала проходят там. Результаты стенда не выдавать за проверку конкретной host-конфигурации: непроверенные на ней сценарии обозначать отдельно.

Для применимых сценариев повторить TCP, UDP, IPv4, IPv6; новые и уже открытые потоки. Начальная серия: не менее 20 управляемых циклов disconnect/reconnect; серия не доказывает универсальную безопасность, число и интервалы записать. Любой прямой пакет — провал, даже без успешного ответа.

| ID | Сценарий | Ожидание и обязательное доказательство |
| --- | --- | --- |
| T01 | VPN работает | probe получает ответ только через VPN; контрольный EXE работает |
| T02 | VPN отключён вручную | новые соединения и дальнейшие данные не выходят напрямую |
| T03 | VPN аварийно прекращает работу | то же, включая непрерывный UDP и удерживаемый TCP |
| T04 | Connected, сервер недоступен | нет fallback; способ blackhole согласовать отдельно |
| T05 | VPN восстановлен | новые запросы снова проходят; разорванный TCP вправе требовать reconnect |
| T06 | Перезагрузка Windows | правила существуют и активны без ручного запуска guard; проверить ранний запуск probe |
| T07 | guard завершён/убит | активная политика остаётся; прерывание транзакции не открывает доступ |
| T08 | Адаптер исчез/создан заново | нет доверия новому по имени; безопасное восстановление либо явный блокирующий пробел |
| T09 | Wi-Fi отключён/подключён | нет прямой передачи после переподключения; проверить Ethernet fallback |
| T10 | Маршрут сменён при открытом потоке | ни одного прямого пакета; отдельные connected UDP и SendTo |
| T11 | IPv6, dual stack, IPv4-mapped | нет прямого IPv6; если VPN без IPv6 — IPv6 блокируется |
| T12 | Локальный прокси и loopback | default deny; разрешённый режим только с доказанным защищённым egress прокси |
| T13 | DNS с пустым кэшем | уникальное тестовое имя; нет прямого DNS, включая системный сервис |
| T14 | Дочерний EXE и общий Node | явно выявляется непокрытый путь; чужой Node не блокируется |
| T15 | Ошибки install/update | сбой на каждой стадии, неясный commit, crash: старое покрытие сохранено |
| T16 | Чужие фильтры и приложения | без новых ограничений от guard; конфликт hard permit выявлен |
| T17 | disable/uninstall/reinstall | удалены только свои объекты, повторная операция идемпотентна |
| T18 | Обновление пути Claude | новый путь не объявляется защищённым автоматически |
| T19 | Входящий поток к probe | исключён обход через ответы в inbound-originated flow; если не доказано — запретить приём |

Для T06 не утверждать защиту до старта BFE на основании persistent. Для T08 различать тот же адаптер с новым LUID и новый GUID. Для T16 не ставить конфликтующие правила сторонних продуктов без отдельного согласования; нужные эксперименты — изолированный стенд.

`guard test` по умолчанию выполняет безопасные проверки состояния/плана. Он не должен сам выключать VPN, менять маршруты, перезагружать ПК или устанавливать правила. Активные проверки — отдельные явно обозначенные параметры и предварительное разрешение.

Отчёт `docs/verification.md`: дата, build ОС, commit программы, хеш EXE/конфигурации, точные действия, ожидаемое/наблюдаемое, ссылки на локальные артефакты, статус каждого ID: PASS / FAIL / NOT RUN / BLOCKED / NOT APPLICABLE с причиной. Для недоступного IPv6 использовать NOT RUN, а не PASS. При обнаружении утечки сохранить доказательства, не устанавливать политику на Claude, вернуться к P2.

## 11 P7 Применить к Claude и завершить документацию

После G3 составить явный перечень image paths и путей обхода. Общий `node.exe` не блокировать; если требуется, предложить выделенную поддерживаемую установку runtime с отдельным реальным путём. Копирование одного launcher не изолирует дочерние процессы.

Для Desktop проверить помощники, обновления, локальные связи и входящие ответы. Для Code проверить обычный запрос, субагента и инструменты с собственными сетевыми соединениями. Не запускать платные действия или отправлять пользовательские данные ради диагностики без разрешения. Отдельные вкладки Chrome вне MVP.

Согласовать применение к реальным EXE, затем повторить относящиеся к ним проверки. Документировать предел: защита выбранных путей не равна произвольному дереву процессов; обновление приложения может потребовать повторной диагностики.

README: сборка PowerShell, права, конфигурация, dry-run, установка, чтение status, тестирование, disable, uninstall, аварийное восстановление, поддержанные сценарии и ограничения. Все приводимые команды сборки проверить на фактическом проекте; пример `CGO_ENABLED=0` оформить синтаксисом PowerShell.

## 12 Итоговый критерий готовности

- [ ] Архитектурные вопросы G1 закрыты или пользователь явно согласовал ограничение требований.
- [ ] Сборка Go для Windows amd64 без CGO воспроизводима; версии зависимостей закреплены.
- [ ] Unit-тесты и dry-run проходят, отсутствуют глобальные блокировки и неявные исключения.
- [ ] Все обязательные сценарии имеют сетевые доказательства; нет прямого выхода и необъяснённых пакетов.
- [ ] После reboot политика активна, после crash остаётся; автоматическое восстановление интерфейса соответствует требованию.
- [ ] DNS, proxy, IPv6, дочерние процессы и обновляемые пути оценены отдельно.
- [ ] Контрольные приложения сохраняют доступ в доступной сети; чужие WFP-объекты не изменены.
- [ ] Восстановление испытано; документация честно различает подтверждённое и непроверенное.

Невыполненный обязательный пункт означает исследовательский прототип, а не готовый kill switch. Коммит и push — только по прямой просьбе пользователя.
