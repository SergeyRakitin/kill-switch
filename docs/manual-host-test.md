# Простой ручной тест на рабочей машине

## Короткий порядок для пользователя

1. Закройте обычное окно `guard-desktop.exe` и запустите его заново через «Запуск от имени администратора». Это не отключает VPN и не меняет правила. Нажмите «Обновить статус»: при `ERROR_ACCESS_DENIED` остановитесь, не запускайте проверку записи WFP и не применяйте план. Если ошибка сохранилась под администратором, сохраните диагностику — причина тогда не ограничивается обычным запуском без повышения.
2. Выберите внешний HTTPS URL, который отвечает до установки. Из каталога `dist` запустите `guard-probe.exe --mode https-monitor --target 'https://ВАША-ЦЕЛЬ/' --count 0 --interval 2s --timeout 5s` и дождитесь успешных ответов.
3. В `guard-ui.json` включите только `probe`; у остальных записей поставьте `enabled:false`. В повышенном `guard-desktop.exe` проверьте путь probe и заданный GUID, откройте «Что изменится в WFP» и примените правила только для probe после отдельного предпросмотра установки. Если план показывает удаление старых правил для других EXE, проверьте это до подтверждения.
4. Убедитесь, что ответы продолжаются. Сами выключите VPN и наблюдайте конкретные ошибки и «Ответы прекратились». Сами включите VPN; монитор не останавливается и может показать «Ответы возобновились».
5. Если «Состояние» сообщает об изменении LUID, заново проверьте план и примените правила. Остановите монитор `Ctrl+C`, нажмите «Удалить правила» и проверьте фактическое состояние.

В списке интерфейсов по умолчанию остаются AmneziaVPN, физические Wi-Fi/Ethernet и другие VPN. Поле `networkAdapterTypes` в `guard-ui.json` принимает `amnezia-vpn`, `physical`, `other-vpn`; после изменения JSON перезапустите GUI. Текущий выбранный GUID не скрывается.

Журналы EXE находятся в `dist/logs` либо в пути `logDir` из `guard status`. Внешний URL не выбирается программой автоматически. Пользователь прошёл функциональный цикл VPN, повторил его с закрытым GUI, проверил незатронутый контрольный EXE и сохранение правил после перезагрузки.

Уточнение пользователя от 4 ноября 2026: отдельного стенда нет. Требуется функциональная проверка на обычной машине, с правилами только для `guard-probe.exe`. Пользователь сам выключает и включает VPN и смотрит вывод/журнал probe. Этот сценарий не должен быть заблокирован требованием отдельного стенда или отдельного hostname.

Это разрешение реализовать сценарий. Агент не должен сам отключать VPN, применять ограничения к Codex/Claude или запускать сетевые мутации в рамках подготовки кода. Пользователь управляет тестом вручную.

## Поведение приложения

1. Выбран только существующий `guard-probe.exe`; остальные приложения выключены. До применения показать точный путь и что правила относятся только к нему. Если ранее установлены собственные правила для других приложений, явно показать предстоящие удаления/замены, не скрывать их за режимом «только probe».
2. Probe выполняет повторные запросы к явно заданной пользователем внешней тестовой цели и пишет время, номер попытки, успех/ошибку, длительность. Не завершать весь тест после первого timeout: продолжать до остановки пользователем или заданного числа попыток. Добавить явный режим непрерывного мониторинга; сохранить прежнее поведение разовых CLI-проб для совместимости.
3. Перед применением правил убедиться, что ответы есть. После применения при включённом VPN ответы также должны быть. Если исходная проверка не прошла, тест не готов — отсутствие ответов после установки ничего не доказывает.
4. Пользователь выключает VPN. Probe продолжает попытки и показывает переход «Ответы прекратились», конкретные ошибки и число неуспешных попыток. Не подписывать любой timeout как «WFP успешно заблокировал».
5. Пользователь включает VPN. Probe продолжает попытки и показывает «Ответы возобновились», время восстановления. Основной режим создаёт новое соединение на каждую попытку; после ошибки не пытается бесконечно использовать сломанный сокет. Проверку уже открытого соединения оставить отдельным расширенным режимом.
6. Если при переподключении изменился LUID VPN-интерфейса, интерфейс должен объяснить необходимость обновления правил. Не обещать автоматическое восстановление доступа до реализации безопасного обновления привязки. При изменении GUID не подменять сохранённый GUID молча.
7. Пользователь останавливает тест и может снять правила для probe. После снятия прочитать фактическое состояние и показать результат.

Нельзя требовать собственного сервера только ради простой проверки. Реализовать простой режим HTTPS-запросов к явно указанному пользователем URL, доступному до установки правил; проверять TLS штатно. Для него использовать прямое соединение без прокси из окружения, ограниченные таймауты и размер читаемого ответа. Не отправлять учётные данные, cookies или произвольный payload; не следовать редиректам незаметно на другие цели. Код ответа и ошибку TLS/HTTP различать: полученный HTTP-ответ с ошибочным статусом не равен сетевому timeout. Тестовый URL не выбирать и не опрашивать автоматически в процессе разработки.

Существующие TCP/UDP-режимы с приёмником и проверкой ACK сохранить для расширенных испытаний. Для простого UI достаточно последовательности «Есть ответы → Нет ответов → Есть ответы», событий применения правил и краткой сводки. Журнал сохраняется согласно docs/logging-plan.md.

## Интерпретация результата

Успешный ручной цикл подтверждает наблюдаемое поведение: при включённом VPN выбранная цель доступна probe, при выключенном ответы прекращаются, после восстановления возвращаются. Этот режим не доказывает отсутствие отдельных прямых пакетов, работу всех протоколов, DNS без утечек, уже открытые потоки или защиту после reboot. Эти расширенные проверки не являются обязательным условием запуска простого ручного теста и не должны мешать пользователю проверить поведение на своей машине.

Без захвата пакетов/наблюдения маршрута не писать «маркер точно прошёл через VPN» или «утечек нет». В итогах использовать «Функциональный цикл пройден» с фактическими наблюдениями. Кодовые дефекты WFP из ревью всё равно необходимо устранить: упрощение процедуры не отменяет корректность реализации.

## Критерий готовности для Sol

Проверить монитор fake transport: успех → несколько ошибок/таймаутов → успех, остановка, отсутствие параллельно накапливающихся запросов, журнал и UI без зависания. Сетевые unit-тесты используют локальный тестовый сервер. Подготовить понятные шаги ручного запуска пользователем без требования отдельного стенда. Обновить CLI, GUI, README и сообщения, которые пока запрещают этот сценарий. Не выполнять выключение VPN самостоятельно.
