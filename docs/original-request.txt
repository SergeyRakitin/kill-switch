# Задача: разработать минимальный Windows VPN Kill Switch для отдельных приложений  ## 1. Цель проекта  Разработай небольшую, максимально простую и надёжную утилиту для Windows 11, которая предотвращает утечку реального IP-адреса при работе выбранных приложений через AmneziaVPN.  Основные защищаемые приложения: - Claude Code (включая дочерние процессы и субагентов, если они самостоятельно создают сетевые соединения). - Claude Desktop. - Возможность вручную добавить другие приложения по пути к исполняемому файлу.  Основной принцип: **fail-closed**.  Выбранное приложение может передавать данные в интернет только через явно разрешённый VPN-интерфейс. Если VPN отключается, перестаёт передавать трафик или Windows выбирает другой маршрут, защищаемое приложение не должно получить возможность прямого подключения через Wi-Fi, Ethernet или иной недоверенный интерфейс.  Остальные приложения Windows должны продолжать работать без ограничений со стороны нашей утилиты.  Это персональный инструмент для одной конкретной Windows-конфигурации. Не нужно разрабатывать универсальный корпоративный фаервол.  ## 2. Моя конфигурация  - ОС: Windows 11 x64. - VPN-клиент: **AmneziaVPN**, не отдельное приложение WireGuard. - VPN-серверы: собственные серверы, возможно два или больше. - Туннель: виртуальный адаптер, создаваемый AmneziaVPN. Фактический протокол и драйвер нужно определить при диагностике, не предполагая заранее WireGuard. - Обычно маршрутизация постоянная и не меняется, кроме обычных подключений и отключений VPN. - Могут быть другие сетевые интерфейсы: Wi-Fi, Ethernet, Tailscale, рабочие VPN. - Разработка ведётся в VS Code на Windows. - Не установлена Visual Studio и отдельный компилятор C++. - Предпочтительный язык — Go. - Желательно обходиться стандартными системными API Windows без дополнительного драйвера и CGO.  В пользовательских настройках должны задаваться:  1. Защищаемые исполняемые файлы. 2. Разрешённый VPN-интерфейс. 3. Необязательный список доверенных IP-адресов VPN-серверов. 4. Включение и отключение защиты.  Список IP VPN-серверов нельзя путать с адресами назначения защищаемых приложений или публичным адресом выхода после NAT. Используй его только там, где такая проверка технически обоснованна. Если без постоянного мониторинга невозможно надёжно проверить выбранный VPN-сервер, объясни это и не добавляй ненадёжную имитацию защиты.  ## 3. Архитектура  Основной механизм — Windows Filtering Platform (WFP).  Требования:  - Постоянные фильтры (`FWPM_FILTER_FLAG_PERSISTENT`). - Привязка правил к конкретным приложениям. - Ограничение разрешённого сетевого пути конкретным VPN-интерфейсом. - Поддержка IPv4 и IPv6. - Отсутствие зависимости от статуса `Connected` в AmneziaVPN. - Отсутствие периодической проверки IP для основной безопасности. - Защита продолжает действовать после завершения GUI/CLI. - Защита восстанавливается после перезагрузки Windows. - Ошибка при установке или обновлении правил не должна оставлять защищаемые приложения с неограниченным интернет-доступом.  Сначала исследуй, какие именно WFP layers и filter conditions нужны для выполнения этих требований.  Особенно важно правильно реализовать: - Идентификацию приложения через `FWPM_CONDITION_ALE_APP_ID`. - Проверку исходящего интерфейса. - IPv4 и IPv6. - Арбитраж `PERMIT` и `BLOCK` между фильтрами и sublayers. - Повторную авторизацию соединений при изменении маршрута. - Постоянство фильтров. - Разрешение loopback только там, где оно безопасно. - Применение новых правил без временного открытия прямого доступа.  Не предполагай, что `Allow`-фильтр для VPN автоматически отменяет `Block`-фильтр для всего остального.  Не добавляй правила с системными исключениями, которые открывают обход защиты, без технического обоснования.  Не разрабатывай собственный kernel driver, если штатных WFP API достаточно.  ## 4. Исследование существующих реализаций  Перед программированием изучи:  **Основная библиотека:** https://github.com/tailscale/wf  **Референсные реализации:** https://github.com/mullvad/mullvadvpn-app https://github.com/WireGuard/wireguard-windows https://github.com/amnezia-vpn/amnezia-client https://github.com/amnezia-vpn/amneziawg-windows-client  **Близкие по назначению проекты:** https://github.com/gruskry/claude-vpn-guard https://github.com/tianhuojeff/claude-vpn-guard https://github.com/ef1m03/kordon https://github.com/henrypp/simplewall  Официальная документация: https://learn.microsoft.com/en-us/windows/win32/fwp/  Не переписывай большие проекты целиком.  Выясни, можно ли безопасно использовать библиотеку Tailscale `wf` для постоянных фильтров по приложениям и интерфейсам.  Если нужных функций нет, допустимо использовать прямые вызовы Windows WFP API из Go.  Если Go потребует слишком сложного низкоуровневого кода, оцени C#/.NET как альтернативу. Но не меняй технологию без конкретной причины.  ## 5. Минимальный интерфейс  Первая версия может быть консольной.  Предлагаемые команды:  - `guard diagnose` — обнаружить интерфейсы, VPN и пути приложений. - `guard install` — установить защиту. - `guard status` — показать текущую защиту и установленные фильтры. - `guard test` — безопасно проверить основные сценарии. - `guard disable` — явно отключить защиту с подтверждением. - `guard uninstall` — удалить только фильтры нашей утилиты.  Конфигурация в JSON или TOML.  Позже можно добавить минимальный GUI, но не использовать Electron или веб-сервер ради нескольких настроек.  Важнее надёжное сетевое ядро, чем красивый интерфейс.  ## 6. Обнаружение приложений  Не считай, что все соединения Claude Code принадлежат процессу `claude.exe`.  Нужно исследовать: - Фактический исполняемый файл Claude Code в моей установке. - Способ запуска Claude Desktop. - Дочерние процессы и субагентов. - Возможные Node.js-процессы. - Возможные локальные прокси. - Сетевые соединения вспомогательных процессов.  Не блокируй глобально `node.exe`, если он используется другими проектами.  Если безопасно и точно определить необходимые процессы невозможно, покажи ограничение и предложи минимальный способ их изоляции. Не объявляй защиту полной без проверки.  Для Chrome не нужно реализовывать защиту отдельных вкладок в первой версии. Допускается защищать отдельный экземпляр браузера, если удастся обеспечить его изоляцию.  ## 7. DNS и локальные прокси  Проверь, какие сетевые соединения реально выполняются защищаемым приложением, а какие могут выполняться от имени системных служб или локальных прокси.  Нельзя считать блокировку одного исполняемого файла доказательством отсутствия всех утечек.  Если обнаружится необходимость системных DNS-исключений или особых правил для прокси, сначала исследуй их последствия.  Не изменяй глобальные настройки DNS Windows без необходимости.  ## 8. Поведение при отказах  Проверь следующие сценарии:  1. AmneziaVPN подключён и нормально работает. 2. VPN отключён вручную. 3. VPN аварийно отключился. 4. VPN показывает `Connected`, но сервер не отвечает. 5. VPN восстановился после обрыва. 6. Windows перезагрузилась. 7. Утилита завершилась аварийно. 8. Виртуальный VPN-интерфейс исчез и появился снова. 9. Wi-Fi отключился и подключился обратно. 10. Изменился маршрут выхода в интернет. 11. Используется IPv6. 12. Claude пытается подключиться через локальный прокси.  При отказе VPN защищаемые приложения должны терять сетевой доступ без переключения на физический интерфейс.  После восстановления правильного VPN-маршрута доступ должен восстановиться без ручного удаления правил.  Никакой автоматической разблокировки по тайм-ауту.  ## 9. Проверка безопасности  Для испытаний сделай отдельную безопасную тестовую программу, которая пытается создавать TCP/UDP-соединения.  До проверки на ней не применяй экспериментальную конфигурацию к реальному Claude.  Проверки должны включать:  - Анализ фактического интерфейса исходящего трафика. - Захват пакетов на физическом интерфейсе. - IPv4. - IPv6. - DNS. - TCP и UDP. - Уже открытые соединения при отключении VPN. - Новые соединения после отключения VPN. - Перезапуск приложения и Windows. - Остановку процесса нашей утилиты.  Не используй только HTTP-запрос к сервису определения IP в качестве доказательства безопасности.  Отчёт должен явно различать: - Тесты, которые реально выполнены. - Тесты, которые нельзя провести автоматически. - Предположения. - Известные ограничения.  ## 10. Безопасность установки  Это важно, потому что утилита будет работать с системными сетевыми фильтрами.  - Не изменяй посторонние правила Windows Firewall. - Используй собственный WFP provider/sublayer с постоянным идентификатором. - Все созданные объекты должны принадлежать нашей утилите. - Предусмотри откат при ошибке. - Предусмотри возможность аварийного удаления правил из повышенной консоли. - Не отключай Windows Firewall и Base Filtering Engine. - Не устанавливай сторонние драйверы без согласования. - Не изменяй сетевую конфигурацию AmneziaVPN. - Все операции изменения системной конфигурации должны быть явно обозначены.  Сначала реализуй режим диагностики и dry-run.  ## 11. Что не нужно  Не нужны:  - VPN-клиент. - Управление подключением AmneziaVPN. - Собственный VPN-протокол. - Сложная служба мониторинга. - Проверка внешнего IP каждые несколько секунд. - Автоматическое переключение серверов. - Обширная система логирования пользовательской активности. - Многооконный GUI. - Electron. - Собственный драйвер Windows. - Полноценный фаервол для всех приложений.  Предпочтительна простая архитектура с минимальным количеством зависимостей.  ## 12. Порядок работы  **Этап 1. Исследование**  Изучи реальную конфигурацию моего Windows-компьютера доступными средствами, в режиме read-only:  - Сетевые интерфейсы. - AmneziaVPN. - Маршруты. - DNS. - Процессы Claude. - Версии Windows. - Возможности библиотек.  Никаких изменений системы на этом этапе.  **Этап 2. Архитектура**  Подготовь короткий технический документ с конкретными WFP layers, conditions, weights и правилами.  Отдельно докажи, что предлагаемая комбинация фильтров действительно блокирует прямые исходящие соединения и не создаёт fail-open при исчезновении VPN.  Если доказать это нельзя, не переходи к утверждению, что реализация безопасна. Пересмотри архитектуру.  **Этап 3. Реализация**  Создай минимальный Go-проект.  Предпочтение одному исполняемому файлу, малому числу зависимостей и понятной структуре исходников.  **Этап 4. Тестирование**  Сначала unit-тесты и dry-run, затем тесты с отдельной тестовой программой.  Изменения системных правил и тесты с отключением VPN проводи только после моего явного разрешения.  **Этап 5. Документация**  Подготовь README: - Как собрать проект. - Как установить. - Как указать приложения и VPN-интерфейс. - Как проверить фильтры. - Как безопасно отключить защиту. - Как восстановить сеть при ошибке. - Какие сценарии доказанно защищены, а какие нет.  ## 13. Главный критерий готовности  Защищаемое приложение никогда не должно успешно устанавливать прямое внешнее соединение через недоверенный интерфейс в протестированных сценариях.  Другие приложения не должны терять доступ к интернету из-за нашей политики.  Приложение должно оставаться максимально простым.  Сначала выполни исследование архитектуры, затем реализуй проект. Не создавай иллюзию надёжности с помощью проверок внешнего IP, таймеров и автоматической приостановки процессов.  Если штатных механизмов Windows недостаточно для заявленной гарантии, прямо укажи конкретное ограничение и предложи минимальную безопасную альтернативу.
