# Kill Switch For Windows

Персональная утилита для Windows 11: выбранные приложения выходят в сеть только через заданный VPN-интерфейс. Если VPN отключился или Windows выбрала другой маршрут, эти приложения теряют доступ в сеть, а остальные программы работают как обычно. Ограничения реализованы штатными правилами **Windows Filtering Platform (WFP)** — системного механизма фильтрации сети Windows.

Проект рассчитан прежде всего на AmneziaVPN, но в интерфейсе можно выбрать и другой VPN-адаптер. Собственный драйвер и фоновая служба не устанавливаются: правила WFP постоянные и действуют без запущенного окна утилиты, в том числе после перезагрузки.

## Рекомендация: начните с правила по имени EXE

В первую очередь задайте правило **по имени EXE** — обычно его достаточно. Оно совпадает с файлом в любой папке, поэтому защита не теряется, когда обновление кладёт новую версию приложения в новый каталог.

| Приложение | Что добавить по имени |
| --- | --- |
| Claude Desktop, Claude Code, Claude CLI | `claude.exe` |
| Cowork в Claude Desktop | `cowork-svc.exe` |

Точный путь нужен, только если требуется ограничить одну конкретную копию файла. Правило по MSIX-пакету подходит лишь для приложений в изолированной песочнице Windows (AppContainer); Claude Desktop к ним не относится.

## Возможности

- Графический интерфейс `guard-desktop.exe` на Wails, React и TypeScript.
- Три способа указать приложение: по имени EXE в любой папке, по точному пути к EXE и по MSIX-пакету.
- Постоянные правила WFP, которые сохраняются после закрытия приложения и перезагрузки Windows.
- Выбор VPN-интерфейса по GUID; служебные и виртуальные адаптеры можно скрыть.
- Предпросмотр изменений перед установкой и подтверждение отпечатка плана.
- Атомарное обновление собственных правил в одной WFP-транзакции.
- Консольный `guard.exe` для диагностики, установки, проверки состояния и удаления правил.
- Тестовый `guard-probe.exe` для проверки потери и восстановления доступа без использования реальных приложений.
- JSONL-журналы операций и сетевых попыток.

## Режимы защиты

Все три режима создают одинаковый набор фильтров (раздел «Набор фильтров» ниже) и различаются только условием, по которому WFP узнаёт приложение.

### По имени EXE — рекомендуемый

В GUI: панель **«EXE по имени»**, кнопка **«Добавить по имени»**. В JSON: `"type": "name"`, в `path` — только имя файла. В CLI: `--file-name`.

WFP знает каждое приложение по пути к его файлу (условие `FWPM_CONDITION_ALE_APP_ID`) и хранит этот путь в нижнем регистре в виде пути устройства:

```text
\device\harddiskvolume3\program files\windowsapps\claude_4.23118.1.0_x64__pzs8sxrjxfjjc\app\claude.exe
\device\harddiskvolume3\users\<пользователь>\appdata\roaming\claude\claude-code\2.1.321\d020ce1b5d30\claude.exe
```

Правило сравнивает **конец** этого пути со строкой `\claude.exe`. Для этого используется сравнение WFP `FWP_MATCH_PREFIX`: по документации Microsoft оно, вопреки имени, проверяет конец значения. Обратная косая черта в начале строки требует совпадения всего имени файла, поэтому `myclaude.exe` под правило не попадает. Значение условия хранится в том же виде, что и путь от `FwpmGetAppIdFromFileName0`: строка UTF-16 с завершающим нулём.

Одно правило `claude.exe` покрывает Claude Desktop, Claude Code и CLI любой версии; после обновлений правила менять не нужно.

Ограничения:

- под правило попадает любой EXE с таким именем в любой папке — такие программы тоже будут выходить в сеть только через VPN;
- если приложение переименует свой EXE, правило перестанет на него действовать;
- имя пишется латиницей, без папки и масок: WFP приводит путь к нижнему регистру, а для не-ASCII символов приведение в программе и в ядре Windows может разойтись;
- дочерние программы с другими именами (git, node для MCP-серверов) нужно добавлять отдельно.

### По точному пути к EXE

В GUI: панель **«Исполняемые файлы (EXE)»**, кнопка **«Добавить EXE»**. В JSON: `"type": "exe"` или без `type`, в `path` — полный путь. В CLI: `--app`.

При установке правил утилита вызывает `FwpmGetAppIdFromFileName0` и получает путь устройства конкретного файла. Условие `FWPM_CONDITION_ALE_APP_ID` сравнивается с ним целиком, поэтому правило действует только на этот файл: копия той же программы в другой папке не ограничивается.

Ограничения: если обновление кладёт приложение в новый каталог, правило остаётся на старом пути, и новая версия выходит в сеть без ограничений, пока правила не установлены заново. Файл должен существовать в момент установки правил.

Подходит для тестового `guard-probe.exe`, для программ с постоянным путём и для случая, когда нужно ограничить одну копию, не затрагивая другие файлы с тем же именем.

### По MSIX-пакету

В GUI: панель **«Windows App (MSIX)»**, кнопка **«Добавить MSIX»** — список установленных пакетов или ручной ввод. В JSON: `"type": "msix"`, в `path` — package family, например `Microsoft.WindowsCalculator_8wekyb3d8bbwe`. В CLI: `--package-family`.

Утилита вычисляет SID пакета через `DeriveAppContainerSidFromAppContainerName` и создаёт условие `FWPM_CONDITION_ALE_PACKAGE_ID`. По документации Microsoft это SID контейнера приложения (AppContainer — изолированная песочница Windows). Правило не зависит от номера версии в каталоге `WindowsApps`.

Ограничения: правило действует **только на процессы внутри AppContainer** — классические приложения Microsoft Store (UWP). Обычные приложения в MSIX-упаковке работают вне песочницы и под правило не попадают. Так устроен Claude Desktop: у всех его процессов есть пакет `Claude_…_pzs8sxrjxfjjc`, но нет AppContainer, а `claude.exe` Claude Code пакета не имеет вовсе. Для Claude используйте правила по имени. На реальной системе режим MSIX не проверялся.

## Как работают правила WFP

### Идентификация VPN

В настройках сохраняется **GUID** VPN-интерфейса — его постоянный идентификатор конфигурации. Перед построением правил Windows преобразует GUID в **LUID** — числовой идентификатор интерфейса для WFP. Если Windows назначает новый LUID после переподключения, приложение предлагает повторно применить план.

Утилита создаёт собственные постоянные provider и sublayer с фиксированными GUID. Вес sublayer — `0x8000`. Чужие правила Windows Firewall и других программ не изменяются.

### Набор фильтров

Для каждого приложения формируются следующие фильтры:

| Слой WFP | Действие | Вес | Условия |
| --- | --- | ---: | --- |
| `ALE_AUTH_CONNECT_V4` / `V6` | `PERMIT_SOFT` | 200 | Приложение, next-hop равен LUID выбранного VPN, соединение не loopback |
| `ALE_AUTH_CONNECT_V4` / `V6` | `BLOCK` | 100 | Приложение |
| `ALE_AUTH_RECV_ACCEPT_V4` / `V6` | `BLOCK` | 100 | Приложение |

«Приложение» — условие выбранного режима: окончание пути `\имя.exe`, полный путь к EXE или SID пакета.

Разрешающий фильтр создаётся только для семейства адресов, у которого обнаружен маршрут через выбранный интерфейс. Если GUID не найден, описание интерфейса не совпадает или маршрута нет, разрешение не добавляется, а блокирующие правила остаются.

При типичном VPN только с IPv4 получается пять фильтров на приложение: одно разрешение исходящих IPv4-соединений, блокировка исходящих IPv4/IPv6 и блокировка входящих IPv4/IPv6. При наличии маршрута IPv6 через VPN добавляется отдельное разрешение IPv6.

Блокирующие фильтры `RECV_ACCEPT` запрещают входящие потоки и ответы в потоках, инициированных извне. Широкого разрешения loopback нет.

### Что происходит при отключении VPN

Блокирующие фильтры продолжают действовать. Разрешающий фильтр привязан к LUID VPN и не разрешает выход через Wi-Fi, Ethernet или другой физический интерфейс. После восстановления того же VPN-пути новые соединения снова разрешаются; при смене LUID нужно повторно применить правила.

### Установка правил

1. Приложение строит предпросмотр плана и показывает добавления и удаления.
2. Пользователь подтверждает отпечаток плана и ревизию конфигурации.
3. Перед транзакцией повторно проверяются план, LUID и текущий набор собственных объектов.
4. Изменения выполняются одной WFP-транзакцией; при любой ошибке она откатывается целиком.
5. После commit состояние читается повторно и сравнивается с ожидаемым.

Зелёный статус означает совпадение структуры правил и доступность выбранного VPN. Он не является доказательством отсутствия всех сетевых утечек.

## Установка

### Требования

- Windows 11 x64.
- VPN-клиент, например AmneziaVPN.
- Microsoft WebView2 Runtime для графического интерфейса.
- Права администратора для чтения и изменения WFP.

Для сборки из исходников дополнительно нужны:

- Go 1.26 или новее;
- Node.js 24 и npm;
- `windres` из MinGW/binutils для встраивания Windows manifest.

Go и `windres` должны находиться в `PATH`, либо пути к ним передаются параметрами сборки.

### Сборка

```powershell
git clone https://github.com/SergeyRakitin/kill-switch.git
Set-Location '.\kill-switch'
.\scripts\build-desktop.ps1
```

Если инструменты не находятся в `PATH`:

```powershell
.\scripts\build-desktop.ps1 `
  -GoExe 'C:\Program Files\Go\bin\go.exe' `
  -WindresExe 'C:\tools\mingw64\bin\windres.exe'
```

Первая команда устанавливает frontend-зависимости через `npm ci`. Для повторной сборки без переустановки зависимостей:

```powershell
.\scripts\build-desktop.ps1 -SkipInstall
```

В каталоге `dist` появятся:

- `guard-desktop.exe` — графический интерфейс;
- `guard.exe` — консольное управление;
- `guard-probe.exe` — безопасный тестовый клиент.

При первом запуске рядом создаётся `guard-ui.json`. Сборка не меняет VPN и не устанавливает WFP-правила.

## Первый запуск и использование

1. Запустите `dist\guard-desktop.exe` через **«Запуск от имени администратора»**: без прав администратора WFP недоступна.
2. В разделе настроек выберите VPN-интерфейс.
3. На главной добавьте приложения. Рекомендуемый способ — **«Добавить по имени»** в панели «EXE по имени»: для Claude это `claude.exe` и `cowork-svc.exe`. Для точного пути есть **«Добавить EXE»**, для пакетов — **«Добавить MSIX»**. Служебный `probe` включён по умолчанию и не удаляется.
4. Нажмите **«Обновить статус»**. При `ERROR_ACCESS_DENIED` не продолжайте установку.
5. Откройте **«Что изменится в WFP»** и проверьте приложения, VPN-интерфейс, добавляемые и удаляемые фильтры. Предпросмотр ничего не меняет.
6. Нажмите **«Установить правила»** и подтвердите просмотренный план.
7. Проверьте состояние provider, sublayer и фильтров в разделе **«Правила WFP»**.

Дополнительная кнопка **«Проверить запись в WFP»** в разделе «Диагностика» создаёт и удаляет служебные provider/sublayer без сетевых фильтров. Она проверяет доступ к WFP, а не VPN и не трафик. Если собственные объекты уже существуют, проверка отклоняется без изменений.

### Повседневная работа

- Переключатель приложения меняет только желаемую конфигурацию. После изменений нажмите **«Установить правила»** ещё раз.
- Предупреждение о неприменённых изменениях означает, что JSON и установленная политика различаются.
- Закрытие окна и выход из трея **не удаляют правила**.
- После переподключения VPN обновите статус. Если LUID изменился, повторите предпросмотр и установку.
- Кнопка **«Удалить правила»** снимает собственные фильтры после подтверждения.

## Настройка через JSON

Обычно достаточно графического интерфейса. После ручного изменения `guard-ui.json` перезапустите приложение.

```json
{
  "schemaVersion": 1,
  "vpnInterfaceName": "AmneziaVPN",
  "vpnInterfaceGuid": "{ВАШ-GUID}",
  "networkAdapterTypes": [
    "amnezia-vpn",
    "physical",
    "other-vpn"
  ],
  "targets": [
    {
      "id": "probe",
      "path": "guard-probe.exe",
      "enabled": true
    },
    {
      "id": "custom-name-claude",
      "type": "name",
      "path": "claude.exe",
      "enabled": true
    },
    {
      "id": "custom-name-cowork",
      "type": "name",
      "path": "cowork-svc.exe",
      "enabled": true
    },
    {
      "id": "custom-tool",
      "path": "C:\\Apps\\tool.exe",
      "enabled": false
    },
    {
      "id": "custom-msix-calculator",
      "type": "msix",
      "path": "Microsoft.WindowsCalculator_8wekyb3d8bbwe",
      "enabled": false
    }
  ]
}
```

- `type` — режим: `name` (имя EXE), `exe` (точный путь; значение по умолчанию) или `msix` (package family).
- `path` — имя EXE, полный путь или package family соответственно. Относительный путь `probe` отсчитывается от каталога с EXE.
- `networkAdapterTypes` — категории адаптеров в списке: AmneziaVPN, физические Wi-Fi/Ethernet и другие VPN.
- Служебная запись `probe` обязательна. Остальные записи можно добавлять, выключать и удалять; их `id` начинаются с `custom-`.

## Проверка на тестовом клиенте

Сначала проверьте правила на `guard-probe.exe`, а не на реальных приложениях. При включённом VPN и установленных правилах запустите в PowerShell из каталога `dist`:

```powershell
& '.\guard-probe.exe' --mode https-monitor --target 'https://example.com/' --count 0 --interval 2s --timeout 5s
```

`--count 0` означает непрерывный монитор. Каждая попытка создаёт новое HTTPS-соединение без прокси из окружения.

Ожидаемый цикл:

1. При включённом VPN выводятся `status=200` и `error=<nil>`.
2. После ручного выключения VPN появляются сетевые ошибки и **«Ответы прекратились»**.
3. После включения VPN появляются успешные ответы и **«Ответы возобновились»**.
4. Монитор останавливается клавишами `Ctrl+C` и выводит итог.

Чтобы проверить именно правило по имени, скопируйте `guard-probe.exe` под уникальным именем в две разные папки и добавьте это имя через «Добавить по имени». Без VPN обе копии должны блокироваться, а копия с другим именем — работать как обычно. Подробный сценарий: [docs/manual-host-test.md](docs/manual-host-test.md).

Успешный цикл подтверждает наблюдаемое поведение новых HTTPS-соединений, но не заменяет захват пакетов и расширенные испытания.

## Консольное управление

Команды выполняются из каталога `dist`; операции WFP требуют PowerShell с правами администратора.

```powershell
# Диагностика интерфейсов, маршрутов и DNS без изменений
& '.\guard.exe' diagnose --json

# Список установленных Windows App / MSIX без изменений
& '.\guard.exe' packages --json

# Фактическое состояние собственных объектов WFP
& '.\guard.exe' status

# Только предпросмотр; в JSON будет fingerprint плана
& '.\guard.exe' install --dry-run --file-name 'claude.exe' --file-name 'cowork-svc.exe' --vpn-guid '{GUID}'
& '.\guard.exe' install --dry-run --app 'C:\Apps\tool.exe' --vpn-guid '{GUID}'
& '.\guard.exe' install --dry-run --package-family 'Microsoft.WindowsCalculator_8wekyb3d8bbwe' --vpn-guid '{GUID}'

# Установка ранее просмотренного плана
& '.\guard.exe' install --file-name 'claude.exe' --file-name 'cowork-svc.exe' --vpn-guid '{GUID}' --plan-fingerprint '<FINGERPRINT>' --yes

# Удалить собственные фильтры
& '.\guard.exe' disable --yes

# Аварийно удалить собственные фильтры, sublayer и provider без JSON
& '.\guard.exe' uninstall --emergency --yes
```

Несколько приложений передаются повторными `--file-name`, `--app` и `--package-family`. Вместо них можно использовать `--config FILE` с CLI-форматом JSON (поля `fileNames`, `applications`, `packageFamilies`). Установка заменяет все собственные фильтры набором из плана. Перед ней обязательны новый предпросмотр, совпавший `--plan-fingerprint` и `--yes`.

## Журналы

`guard.exe` и `guard-probe.exe` пишут JSONL в `logs` рядом с EXE. Фактический каталог также указан в `logDir` результата `guard status`. Если основной каталог недоступен, используется `%LOCALAPPDATA%\KillSwitch\logs`.

Файл журнала начинается заново после 10 МиБ. Завершённые журналы старше 7 дней удаляются, начиная с самых старых, как и при превышении общего объёма 100 МиБ на компонент; если места всё равно нет, запись прекращается с сообщением в stderr. Пределы меняются переменными окружения `KS_LOG_MAX_MIB`, `KS_LOG_BUDGET_MIB` и `KS_LOG_RETENTION_DAYS`.

В журналах сохраняются время, идентификаторы запуска и операции, длительность, выбранные приложения, GUID/LUID, собственные ключи WFP, результаты сетевых попыток и ошибки. Конфигурация целиком, cookies, содержимое HTTPS-ответов и сетевой payload не записываются.

## Проверено и ограничения

На реальной системе подтверждены:

- для `guard-probe.exe` по точному пути — установка и чтение правил WFP, проверка записи WFP, прекращение новых HTTPS-ответов после выключения VPN и восстановление после включения, работа правил с закрытым GUI, отсутствие ограничений у контрольной копии probe по другому пути, сохранение правил и восстановление доступа после перезагрузки Windows;
- правила по имени EXE — пользователь проверил их на своей машине и подтвердил, что они работают.

Не проверялись: режим MSIX, захват пакетов на физическом интерфейсе, уже открытые TCP/UDP-потоки, DNS, IPv6, прокси, дочерние процессы, входящие потоки и аварийные разрывы VPN.

Это персональный прототип, а не универсальный корпоративный firewall.
